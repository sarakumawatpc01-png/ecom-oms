PART 1 — PRODUCT OVERVIEW & VISION
================================================================================

WHAT IS AGENCYFIC OMS?
-----------------------
Agencyfic OMS is a multi-tenant, web-based order management SaaS platform
built for Indian ecommerce sellers who sell across Meesho, Amazon India, and
Flipkart simultaneously. Instead of logging into three separate seller panels
every day, sellers manage everything — orders, labels, invoices, return claims,
AI-optimized listings, and product images — from one unified dashboard.

The key differentiator vs existing tools (Unicommerce, EasyEcom, Vinculum):
1. Meesho is supported WITHOUT needing Meesho's official API (session-based)
2. Per-order credit pool billing — not per-platform, not per-user
3. AI listing optimization and AI product image generation built-in
4. Evidence capture system for return fraud claims (photos + video)
5. Designed for small-to-mid sellers, not large enterprises
6. Affordable Indian pricing (₹1,000 / ₹4,000 / ₹7,500 per pool)

WHO ARE THE USERS?
------------------
Primary: Indian sellers who sell on Meesho + at least one of Amazon/Flipkart
Secondary: Agency owners managing multiple seller accounts for clients
Size: Sellers processing 500 to 15,000 orders per month

USER PAIN POINTS BEING SOLVED:
1. Logging into 3 separate platforms daily wastes 1-2 hours
2. Meesho dispatch deadlines are missed because sellers forget to check
3. Wrong return fraud — seller has no evidence to file claims
4. Printing labels from 3 platforms separately is chaotic
5. GST invoice generation is manual and error-prone
6. Product listings are poorly optimized, hurting search visibility
7. Product images are low quality (phone photos, bad backgrounds)

COMPONENT BREAKDOWN:
---------------------

1. NGINX
   - Listens on port 80 and 443
   - Redirects HTTP to HTTPS
   - Reverse proxies to Next.js (port 3000) and Node API (port 4000)
   - Handles SSL via Let's Encrypt / Certbot
   - Rate limiting at nginx level (100 req/min per IP)

2. NEXT.JS FRONTEND
   - Server-side rendered PWA
   - Works on any browser including mobile
   - "Add to Home Screen" support on Android/iOS
   - Communicates with backend via REST API + Socket.io
   - NO business logic on frontend — purely UI + API calls
   - All routes protected by JWT middleware

3. NODE.JS BACKEND (API Server)
   - REST API on port 4000
   - Endpoints: /auth, /orders, /labels, /invoices, /claims,
     /accounts, /billing, /platforms, /ai, /admin
   - Bull queue manager for async jobs
   - Socket.io server for real-time push to frontend
   - Cron jobs: order sync (every 5 min), session health check (every 6h),
     claim deadline alerts (every hour), billing alerts (daily)

4. POSTGRESQL DATABASE
   - Main persistent data store
   - All tables listed in Part 3
   - PgBouncer connection pooling (for 100+ users)
   - Indexed on: user_id, account_id, order_id, platform, created_at, status

5. REDIS
   - Session cookie cache: key = "session:{user_id}:{account_id}"
   - OTP storage: key = "otp:{email}" with 10 min TTL
   - Trust tokens: key = "trust:{token}" with 30 day TTL
   - Bull queues: order_sync_queue, action_queue, ai_queue, label_queue
   - Rate limiting counters

6. PLAYWRIGHT ENGINE
   - NOT running 24/7
   - Invoked ON DEMAND for:
     a. First login to a Meesho account (capture session cookies)
     b. Session expiry re-login
     c. Order actions on Meesho (accept, pack, ship buttons)
     d. Meesho claim form filling assistance
   - Headless Chromium
   - Each invocation spins up a browser context, does the task, closes it
   - Max 3 concurrent Playwright instances on 8GB VPS to avoid RAM spike

7. BULL QUEUE SYSTEM
   Queue: order_sync_queue
     Workers: 5 concurrent
     Jobs: Fetch orders for one seller account (HTTP call with cookie)
     Schedule: Every 5 minutes, one job per active account

   Queue: action_queue
     Workers: 3 concurrent
     Jobs: Accept/pack/ship order via Playwright
     Priority: HIGH — process within 30 seconds of request

   Queue: label_queue
     Workers: 3 concurrent
     Jobs: Fetch label PDF from Meesho/Flipkart, generate Amazon label
     Priority: MEDIUM

   Queue: ai_queue
     Workers: 2 concurrent
     Jobs: AI listing optimization calls, AI image generation
     Priority: LOW (not time-critical)

   Queue: notification_queue
     Workers: 2 concurrent
     Jobs: Send email, SMS, WhatsApp notifications

REAL-TIME UPDATES (Socket.io):
  - Seller connects → joins room "user:{user_id}"
  - When new order detected: emit "new_order" to that room
  - When order status changes: emit "order_update"
  - When session expires: emit "session_expired" with account details
  - When AI job completes: emit "ai_complete"
  - When Bull job fails: emit "job_error"
  - Frontend listens and updates UI without page refresh

PART 4 — MEESHO INTEGRATION (A TO Z)
================================================================================

WHY NO OFFICIAL API:
---------------------
Meesho does not provide a public API for order management. Their API is
invite-only and given only to approved enterprise aggregators (Unicommerce,
EasyEcom). For everyone else, the only option is session-based automation —
logging into the Meesho Seller Panel (supplier.meesho.com) using the seller's
phone number + password, capturing the session cookies, and using those cookies
to make HTTP calls to Meesho's internal (undocumented) API endpoints.

This is the same method used by Base.com, Fynd Konnect, and other platforms
before they got official API access. It works reliably at moderate scale.

STEP 1 — SELLER ONBOARDING (First Time Account Connection):
------------------------------------------------------------
1. Seller opens Agencyfic OMS dashboard
2. Goes to: Platforms → Meesho → "Connect Account"
3. Form shown:
   - Account Nickname (e.g. "Women's Kurtas Store")
   - Meesho Registered Phone Number
   - Meesho Password
4. Seller submits form
5. Backend receives phone + password
6. Password encrypted with AES-256 before storage:
   encrypted_password = AES.encrypt(plain_password, MASTER_KEY)
   MASTER_KEY is stored as environment variable on VPS, never in DB
7. linked_accounts record created with status = 'connecting'
8. Bull action_queue job created: { type: 'meesho_first_login', account_id }
9. Worker picks up job, invokes Playwright:

PLAYWRIGHT LOGIN FLOW (Code Logic):
   a. Launch headless Chromium browser
   b. Create new browser context (incognito-like)
   c. Navigate to: https://supplier.meesho.com/
   d. Wait for login page to load
   e. Check if password login option exists (it does for returning users)
      — Click "Login with Password" if toggle needed
   f. Fill phone number field
   g. Fill password field
   h. Click Login / Submit button
   i. Wait for navigation (max 10 seconds)
   j. Check result:
      - If redirected to dashboard → SUCCESS
      - If OTP screen shown → FAIL (notify seller to login manually once)
      - If wrong credentials error → FAIL (notify seller to update password)
   k. On SUCCESS: extract all cookies from browser context:
      cookies = await context.cookies()
   l. Serialize cookies to JSON string
   m. Encrypt cookies JSON with AES-256
   n. Store in sessions table
   o. Store in Redis: SET "session:meesho:{account_id}" encrypted_cookies EX 2592000
      (2592000 seconds = 30 days TTL in Redis)
   p. Update linked_accounts: session_status = 'active', last_sync_at = NOW()
   q. Close browser context and browser
   r. Trigger first order sync immediately

PASSWORD LOGIN NOTE:
   Meesho allows returning users to login with phone + password (no OTP).
   This is the key enabler of full automation. If a seller has never used
   password login, they need to set it once in the Meesho app, then provide
   it to our system.

STEP 2 — ORDER SYNC (Runs Every 5 Minutes):
-------------------------------------------
The cron job loops through all active linked_accounts where platform='meesho'
and sync_enabled=true. For each account:

a. Load session cookies from Redis
   If Redis cache miss → load from DB, put back in Redis
b. Decrypt cookies
c. Make HTTP request to Meesho internal API:
   GET https://supplier.meesho.com/api/v2/orders?status=pending&page=1&limit=50
   Headers:
     Cookie: [decrypted cookie string]
     Content-Type: application/json
     User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)...
     Referer: https://supplier.meesho.com/orders
d. Parse response JSON
e. For each order in response:
   - Check if order already exists: SELECT id FROM orders WHERE platform='meesho'
     AND platform_order_id=? AND user_id=?
   - If NEW order:
     * Insert into orders table
     * emit Socket.io event "new_order" to user's room
     * Create notification: "New order #{order_id} on Meesho"
     * If auto_accept_orders=true, queue an accept action
   - If EXISTING order with changed status:
     * Update orders table
     * emit "order_update" event
f. Check if HTTP response was 401 or 403 (session expired):
   * Flag linked_accounts.session_status = 'expired'
   * Send notification: "Your Meesho account '{nickname}' session expired.
     Please reconnect."

STEP 3 — ORDER ACTIONS (Accept / Pack / Ship):
-----------------------------------------------
When seller clicks Accept on an order in the dashboard:

a. Frontend sends: POST /api/orders/{id}/accept
b. Backend validates: JWT valid, order belongs to this user, order is 'pending'
c. Load session cookies from Redis
d. If Meesho allows direct HTTP POST to /api/v2/orders/{id}/accept with cookie:
   → Make direct HTTP call (fastest, <1 second)
e. If that endpoint requires browser interaction:
   → Queue Playwright action job (priority HIGH)
   → Playwright loads order page, clicks Accept button
   → Returns result
f. On success: update orders table status = 'accepted'
g. Deduct 1 credit from user's pool (this is the "counted" event for Meesho)
h. Emit Socket.io "order_update" to frontend

STEP 4 — LABEL DOWNLOAD:
--------------------------
a. Make HTTP GET to Meesho's label URL with session cookie
b. Meesho returns a redirect to label PDF URL
c. Follow redirect, download PDF bytes
d. Store in Cloudflare R2: labels/{user_id}/{order_id}/label.pdf
e. Return download URL to frontend
f. Label stored permanently (never auto-deleted — superadmin setting)

STEP 5 — SESSION HEALTH CHECK (Every 6 Hours):
-----------------------------------------------
Cron job runs for all active Meesho accounts:
a. Make GET to https://supplier.meesho.com/api/v2/seller/profile with cookie
b. If 200 → session still alive → update last_sync_at, do nothing
c. If 401/403 → session expired → trigger re-login with stored password
d. Re-login uses same Playwright flow as Step 1
e. If re-login fails (password changed) → notify seller to update password

STEP 6 — PARALLEL PROCESSING (Rush Hour Mode):
-----------------------------------------------
Seller clicks "Rush Hour Mode" or system detects >20 pending orders:
- Bull action_queue processes up to 9 concurrent jobs (one per linked account)
- Each job handles its own account's pending orders sequentially
- Jobs for DIFFERENT accounts run in parallel (safe — different sessions)
- Jobs for SAME account run sequentially (to avoid race conditions)
- Priority: Claims filing > Order acceptance > Label download > Sync

MEESHO SCALABILITY NOTE:
  All Meesho sessions from all users run from your VPS IP.
  This is identical to how Unicommerce, EasyEcom operate.
  Meesho recognizes this as normal aggregator behavior.
  Risk of ban: LOW for normal order volumes (under 10,000 requests/day).
  At 200 users doing 50 orders/day = 10,000 order syncs = spread over 288
  cron cycles = ~35 API calls per cycle. Completely normal traffic.

8. Receive: Client ID (LWA_APP_ID) and Client Secret (LWA_CLIENT_SECRET)

SELLER ONBOARDING VIA OAUTH:
------------------------------
When a seller clicks "Connect Amazon Account":

1. Your backend generates an OAuth URL:
   https://sellercentral.amazon.in/apps/authorize/consent?
   application_id={YOUR_APP_ID}
   &state={random_state_token}
   &redirect_uri=https://yourdomain.com/oauth/amazon/callback
   &version=beta

2. Seller is redirected to Amazon Seller Central
3. Seller sees your app requesting permissions, clicks "Authorize"
4. Amazon redirects back to your callback URL with:
   ?spapi_oauth_code={AUTH_CODE}&state={state_token}

5. Your backend exchanges auth_code for tokens:
   POST https://api.amazon.com/auth/o2/token
   Body: {
     grant_type: "authorization_code",
     code: AUTH_CODE,
     redirect_uri: YOUR_REDIRECT_URI,
     client_id: LWA_APP_ID,
     client_secret: LWA_CLIENT_SECRET
   }
   Response: {
     access_token: "...",     // expires in 1 hour
     refresh_token: "...",    // never expires
     token_type: "bearer"
   }

6. Store refresh_token encrypted in linked_accounts table
7. Access token cached in Redis with 55-minute TTL
8. Seller ID fetched via: GET /sellers/v1/marketplaceParticipations

HOW TOKEN REFRESH WORKS:
  Before every Amazon API call:
  a. Check Redis for valid access_token for this account
  b. If found and not expired → use it
  c. If expired or not found:
     POST https://api.amazon.com/auth/o2/token
     Body: { grant_type: "refresh_token", refresh_token: decrypted_refresh_token,
             client_id, client_secret }
     Response: new access_token
     Cache in Redis for 55 minutes

ORDER SYNC:
-----------
Every 5 minutes (or via push notification webhook — see below):

GET https://sellingpartnerapi-eu.amazon.com/orders/v0/orders
Headers: x-amz-access-token: {access_token}
Params: MarketplaceIds=AEXKL89LWJ0JX (India), CreatedAfter={5 min ago}, OrderStatuses=Unshipped,PartiallyShipped

Parse response, insert new orders into orders table.
Amazon order status mapping to our status:
  Pending          → 'pending'
  Unshipped        → 'accepted'
  PartiallyShipped → 'packed'
  Shipped          → 'shipped'
  Delivered        → 'delivered'
  Canceled         → 'cancelled'

Credit deduction trigger for Amazon: when seller confirms shipment
(status changes to 'shipped' via our dashboard).

PART 9 — BILLING SYSTEM (Complete Flow)

PRICING STRUCTURE:
  Starter: 1,000 orders — ₹1,000 — ₹1.00/order
  Growth:  5,000 orders — ₹4,000 — ₹0.80/order
  Pro:    10,000 orders — ₹7,500 — ₹0.75/order
  
  Top-ups (mid-plan extra orders):
  500 orders  — ₹600   (₹1.20/order, slight premium)
  1,000 orders — ₹1,100 (₹1.10/order)
  2,000 orders — ₹2,000 (₹1.00/order)

CREDIT POOL MODEL:
  - No monthly subscription. You buy a pool of orders.
  - Pool is shared across ALL platforms (Meesho + Amazon + Flipkart)
  - Pool expires based on superadmin setting (e.g. 90 days or never)
  - When pool exhausts: grace orders kick in (50 free, then billed)
  - Grace orders: ₹1.50/order, billed at next purchase

WHAT COUNTS AS AN ORDER:
  Meesho: Seller accepts order (clicks Accept) = 1 credit
  Amazon: Seller confirms shipment = 1 credit
  Flipkart: Seller marks Ready to Dispatch (RTD) = 1 credit
  
  Does NOT count:
  - Orders cancelled before the counted action
  - Orders auto-cancelled by platform
  - Duplicate orders (protected by UNIQUE constraint on platform_order_id)
  - Synced orders that were just viewed (view = free, action = paid)

RAZORPAY INTEGRATION FLOW:
  
  1. Seller clicks [Buy ₹4,000 — 5,000 orders]
  
  2. Backend creates Razorpay order:
     POST https://api.razorpay.com/v1/orders
     Headers: Basic Auth with Key ID + Key Secret
     Body: {
       amount: 400000,  // in paise (₹4,000 = 400000 paise)
       currency: "INR",
       receipt: "agf-{user_id}-{timestamp}",
       notes: { user_id: "...", plan_id: "..." }
     }
     Response: { id: "order_XXX", ... }
  
  3. Store billing_transaction record: status='pending', razorpay_order_id=order_XXX
  
  4. Frontend receives Razorpay order ID, opens Razorpay Checkout Modal:
     var options = {
       key: "rzp_live_XXXXXXXX",
       amount: 400000,
       currency: "INR",
       name: "Agencyfic OMS",
       description: "Growth Plan — 5,000 orders",
       order_id: "order_XXX",
       handler: function(response) {
         // POST to backend with razorpay_payment_id + razorpay_signature
       },
       prefill: { email: seller.email, contact: seller.phone },
       theme: { color: "#F97316" }
     };
     var rzp = new Razorpay(options);
     rzp.open();
  
  5. Seller pays via UPI / Card / Net Banking
  
  6. On payment success, Razorpay ALSO sends webhook to:
     POST https://yourdomain.com/webhooks/razorpay
     Header: X-Razorpay-Signature (HMAC-SHA256 of body with webhook secret)
     Body: { event: "payment.captured", payload: { payment: {...} } }
  
  7. Webhook handler:
     a. Verify signature: HMAC(body, webhook_secret) === X-Razorpay-Signature
     b. If valid:
        - Update billing_transaction: status='paid', razorpay_payment_id=...
        - UPDATE users SET credits_purchased = credits_purchased + 5000,
          plan_id = growth_plan_id, plan_expires_at = NOW() + INTERVAL '90 days'
        - Generate seller invoice PDF (stored in R2)
        - Send payment confirmation email with invoice attached
        - Socket.io emit "billing_updated" to user's room
     c. If invalid signature: log security event, return 400
  
  NOTE: Verify BOTH frontend response AND webhook. Never update credits
  based on frontend alone (easily spoofed). Webhook is the authoritative source.
  
  8. Frontend receives Socket.io event, updates credits pill immediately

GRACE ORDER BILLING:
  When credits reach 0:
  - grace_orders_used starts incrementing
  - On next purchase, grace bill added automatically:
    e.g. 23 grace orders × ₹1.50 = ₹34.50 added to next invoice
  - Shown in billing as "Grace orders used: 23 × ₹1.50 = ₹34.50 (billed)"

CREDIT ENFORCEMENT MIDDLEWARE:
  Before processing any billable action (accept order, confirm shipment, RTD):
  
  async function checkCredits(userId) {
    const user = await db.query(
      'SELECT credits_purchased, credits_used, credits_grace_used FROM users WHERE id=$1',
      [userId]
    );
    const remaining = user.credits_purchased - user.credits_used;
    if (remaining > 0) return { allowed: true, type: 'standard' };
    if (user.credits_grace_used < GRACE_LIMIT) return { allowed: true, type: 'grace' };
    return { allowed: false, reason: 'credits_exhausted' };
  }
  
  If allowed=false: return 402 Payment Required, frontend shows paywall modal.
  If type='grace': process action + increment credits_grace_used + notify seller.

SUBSCRIPTION INVOICE GENERATION:
  After each successful payment:
  - Your company details (GSTIN, address) from site_settings
  - Seller details (name, GSTIN, address) from users table
  - Plan description, amount, 18% GST breakup
  - Invoice PDF generated using pdfkit or similar
  - Stored in R2: invoices/system/{year}/{invoice_number}.pdf
  - Linked in seller_invoices table
  - Emailed to seller
  - Visible in seller's dashboard under Billing > Invoices from Us

JWT STRUCTURE:
  payload: {
    sub: user_id,
    email: email,
    role: 'seller' | 'sub_user' | 'admin',
    parent_id: null | parent_user_id,  // for sub-users
    sub_role: null | 'admin' | 'order_manager' | 'view_only',
    iat: issued_at,
    exp: issued_at + 86400  // 24 hours
  }
  signed with: HS256(JWT_SECRET from env)

TOKEN REFRESH:
  Frontend checks token expiry 5 minutes before expiry
  If expiry approaching: POST /auth/refresh (with current valid token)
  Backend issues new token (sliding window — extends 24h from each use)

TRUST TOKEN MECHANISM:
  When seller selects "Trust this device for 30 days":
  1. Generate UUID v4 trust token
  2. Store in trusted_devices table with user_id, expires_at (30 days), IP, user_agent
  3. Store in Redis: SET "trust:{token}" "{user_id}" EX 2592000
  4. Set HTTP-only cookie: agencyfic_trust={token}, Max-Age=2592000, Secure, SameSite=Strict
  
  On next login from same device:
  1. Backend reads cookie agencyfic_trust
  2. Check Redis: GET "trust:{token}" → gets user_id
  3. Verify user_id matches email submitted
  4. If match → skip OTP, issue JWT directly
  5. Update trusted_devices.last_used_at

OTP FLOW:
  Generate: Math.floor(100000 + Math.random() * 900000).toString() → 6 digits
  Store: SET "otp:{email}" "{otp}" EX 600 (10 minutes)
  Send via: SendGrid (email only for now, SMS optional)
  Verify: GET "otp:{email}" → compare → DEL "otp:{email}" on match
  Failed attempts: if wrong OTP 5 times → lock for 15 minutes

SUB-USER PERMISSIONS:
  Middleware checks both role AND sub_role in JWT:
  
  Route protection examples:
  GET /api/orders — allowed for all roles
  POST /api/orders/:id/accept — allowed for 'admin' role, 'order_manager' sub_role
                                 NOT allowed for 'view_only'
  GET /api/billing — allowed for owner only (role='seller', no parent_id)
  PUT /api/settings — allowed for owner only
  POST /api/accounts — allowed for owner only (add platform accounts)

PART 13 — EVIDENCE CAPTURE & RETURN CLAIMS SYSTEM
================================================================================

WHY THIS FEATURE IS CRITICAL:
  Indian ecommerce return fraud is a major seller pain point.
  Meesho return fraud rate: approximately 5-15% (industry estimates).
  Common fraud: buyer receives genuine product, returns empty box, claims refund.
  Without evidence: seller loses the claim every time.
  With timestamped packing video: seller wins ~80% of claims.

EVIDENCE CAPTURE FLOW:
  
  Phase 1 — During Packing (Proactive):
  
  1. Seller opens order in dashboard, clicks "Capture Packing Evidence"
  2. System shows camera interface in browser (using getUserMedia API):
     [Record Video] [Take Photos]
     Video: records packing session (seller shows product, packs it, seals box, shows label)
     Photos: 5-6 photos required — front/back of product, sealed box, label closeup
  
  3. File handling for video:
     a. Browser records video using MediaRecorder API (max 3 minutes)
     b. On stop: GET /api/upload-url → backend generates presigned R2 URL
     c. Browser uploads directly to R2: evidence/{user_id}/{order_id}/packing_video.mp4
     d. Browser notifies backend: POST /api/evidence/confirm { r2_key, order_id, type:'video', captured_at }
     e. Backend creates evidence_files record
     f. Backend does NOT handle the binary data — zero RAM usage
  
  4. File handling for photos:
     Same presigned URL flow, one URL per photo
     5 photos × ~500KB each = 2.5MB total, stored in R2
  
  5. After capture: order shows evidence indicator (green camera icon)
  
  Phase 2 — When Return Arrives:
  
  1. System detects return via API/scraping
  2. Creates returns record, sets claim_deadline
  3. Notifies seller: "Return for Order #{id} received. Evidence captured ✅"
  4. Seller navigates to Claims > Active Returns
  5. Clicks [Raise Claim] → 4-step wizard (described in Part 7)

EVIDENCE STORAGE:
  - Photos: stored permanently in R2 (small size, negligible cost)
    5 photos × 500KB × 100 sellers × 50 returns/month = 1.25GB/month
    At R2 pricing ($0.015/GB): $0.02/month. Effectively free.
  - Videos: stored in R2 with TTL = claim_deadline + 30 days (configurable)
    After that: auto-deleted by R2 lifecycle policy
    Maximum storage at any time: ~50GB for 200 active users
    Cost: $0.75/month for 50GB. Negligible.

EVIDENCE FOR DIFFERENT PLATFORMS:
  Meesho:
    - Claim form is on supplier.meesho.com/claims
    - Our system: opens page in new tab, pre-copies claim text to clipboard
    - Seller manually pastes text and uploads photos (downloaded from our system in 1 click)
    - System records: claim_status='raised', platform_claim_id entered by seller
    
  Amazon SAFE-T:
    - Fully automated via API:
    POST /orders/v0/orders/{orderId}/orderItems → get item details
    POST /solicitations/v1/... → SAFE-T claim with evidence
    - Amazon S3 presigned URL for evidence upload
    - System handles entire flow without seller manual action
    - Seller just clicks [Submit to Amazon] → done
    
  Flipkart:
    - Return approval/rejection:
    POST /seller/returns/{return_id}/reject (with reason and evidence reference)
    - For dispute escalation: Flipkart seller support ticket
    - Similar to Meesho: system opens support page, pre-fills details

CLAIM TRACKING (Post-Submission):
  System polls/checks claim status periodically:
  Meesho: scrape /claims page every 6 hours for status updates
  Amazon: poll SAFE-T claim status via API
  Flipkart: check return status via /seller/returns/{id}
  
  Status updates reflected in Claims > Claim History table.
  Notification sent when claim is resolved (won or lost).

  - All labels stored permanently in R2 (configurable in admin settings)

  - Storage: 1 label PDF ≈ 150KB × 100 sellers × 50 orders/day × 30 days = 22.5GB/month cumulative
  - R2 cost: $0.34/month. Completely justified.

INVOICE SYSTEM:
  
  GST Invoice Generation Rules:
  - If seller_state == customer_state: CGST (9%) + SGST (9%)
  - If seller_state != customer_state: IGST (18%)
  - For composition scheme dealers: no GST charged to buyer
  - For unregistered sellers: no GST invoice (just a sales receipt)
  
  Invoice Content:
  Line 1: Invoice Number (e.g. INV-2026-001234)
  Line 2: Invoice Date
  SELLER:
    [GSTIN], [Name], [Address], [State], [Email]
  BUYER:
    [Name], [State], [Pincode]
    (Phone and full address optional — depends on platform privacy)
  ITEMS TABLE:
    | # | Description (product name) | HSN Code | Qty | Rate | Taxable | CGST/SGST/IGST | Total |
  TOTALS:
    Subtotal, CGST amount, SGST amount (or IGST), Grand Total
  FOOTER:
    "This is a computer-generated invoice."
    "Thank you for your purchase."
  
  HSN Code: Set by seller in product/SKU settings. For kurti/women's wear: 6104 or 6211
  (Seller sets this once, system auto-fills on all invoices for that SKU)
  
  Generation Library: pdfkit (Node.js)
  Storage: Permanent in R2: invoices/{user_id}/{year}/{invoice_number}.pdf
  
  Bulk Invoice Download:
  - Select orders → Generate All Invoices
  - System generates PDFs in parallel (Bull queue)
  - Merges into ZIP using archiver (Node.js)
  - Returns ZIP download

PART 16 — SECURITY ARCHITECTURE
================================================================================

DATA ENCRYPTION:
  Passwords: bcrypt with 12 rounds (industry standard)
    Never stored in plaintext. Cannot be reversed.
    Hash stored in users.password_hash
  
  Meesho passwords: AES-256-GCM
    Key: ENCRYPTION_MASTER_KEY environment variable (never in DB)
    Encrypted value stored in linked_accounts.meesho_password_enc
    Decrypted only in memory when needed for Playwright login
    Example:
    const { encrypted, iv, authTag } = AES.encrypt(plaintext, MASTER_KEY);
    stored = iv + ':' + authTag + ':' + encrypted (base64)
  
  Session cookies: AES-256-GCM (same as above)
  OAuth tokens (Amazon/Flipkart): AES-256-GCM
  Third-party API keys (in site_settings): AES-256-GCM
  
  Master encryption key rotation: superadmin can trigger re-encryption
  (decrypts all values with old key, re-encrypts with new key in a transaction)

API SECURITY:
  All API endpoints require valid JWT except: /auth/login, /auth/signup,
  /auth/forgot-password, /auth/reset-password, /webhooks/razorpay
  
  Rate limiting (via express-rate-limit + Redis):
  /auth/login: 5 attempts per 15 minutes per IP
  /auth/verify-otp: 5 attempts per 10 minutes per email
  General API: 100 requests per minute per user
  
  Input validation: all inputs validated and sanitized (express-validator)
  SQL: parameterized queries only, never string concatenation
  XSS: Content-Security-Policy headers, all output HTML-escaped

WEBHOOK SECURITY:
  Razorpay: HMAC-SHA256 signature verification on every webhook
  Amazon SNS: verify against Amazon's published certificate
  Flipkart: verify signature with app secret

HTTPS ENFORCEMENT:
  All HTTP redirected to HTTPS (nginx)
  HSTS header: Strict-Transport-Security: max-age=31536000
  TLS 1.2+ only

SESSION SECURITY:
  JWT stored in memory (not localStorage) to prevent XSS theft
  On mobile/desktop: stored in httpOnly cookie alternative
  Concurrent session limit: configurable (default: no limit, but shown in security tab)
  Session invalidation: on password change, account suspension
